CHECKPOINT 7.23 — FLIGHT RECOVERY PERSISTENCE HARDENING

Checkpoint 7.22 is complete and committed as 8ab65cc.

7.22 successfully integrated Sierra 4 Map V2 as an opt-in production renderer with the classic map retained as default/fallback.

The production regression baseline remains healthy:

- 2,004 automated assertion executions passed
- 0 automated assertion failures
- 2 native simulator checks unavailable
- 9 / 9 recorded-flight replays passed
- 91,366 / 91,366 telemetry samples processed
- Map V2 flight-isolation/contention checks passed
- FlightSessionCoordinator remains authoritative

However, the final 7.22 verification gate correctly remained RED because an intermittent existing flight-recovery persistence failure was detected.

KNOWN FAILURE

FlightRecoveryStore.Save occasionally receives UnauthorizedAccessException during:

File.Move(..., overwrite: true)

The failure was reproduced:

- during Map V2 contention testing
- with the classic renderer
- in a standalone file-replacement probe with no application or map loaded

The standalone probe reproduced approximately 3 failures in 500 replacements.

This currently prevents Map V2 from becoming the default renderer because Sierra 4 cannot claim a clean persistence/recovery verification run while an intermediate recovery checkpoint may fail.

OBJECTIVE

Identify the root cause of the intermittent recovery-file replacement failure and harden flight recovery persistence without changing Sierra 4's recovery semantics, storage location, data format or authoritative flight behavior.

This is a PERSISTENCE RELIABILITY checkpoint.

It is NOT:

- a Map V2 feature checkpoint
- a UI redesign
- a database migration
- a broad storage rewrite
- an authentication checkpoint
- a Flight Tracking redesign
- a Dispatch redesign


PART 1 — ROOT-CAUSE INVESTIGATION

Before modifying production behavior, investigate the failure.

Inspect:

- FlightRecoveryStore
- all callers of recovery Save
- recovery read/load/delete behavior
- temporary-file strategy
- File.Move(... overwrite:true) behavior
- concurrent save possibilities
- concurrent read possibilities
- cleanup/disposal
- antivirus/indexer/file-watcher interaction possibilities
- filesystem semantics on the current Windows environment
- whether multiple application/runtime paths can attempt replacement simultaneously
- whether destination or temporary files can retain handles
- whether test infrastructure itself contributes
- file attributes/permissions
- timing around rapid sequential saves
- crash/restart behavior

Determine whether the failure is caused by:

A. application concurrency
B. incorrect handle lifetime
C. Windows replacement semantics
D. external/transient file locking
E. test behavior
F. another identified cause
G. an unresolved combination

Do not claim a root cause unless supported by evidence.


PART 2 — PRESERVE RECOVERY CONTRACT

The existing recovery contract must remain compatible.

Do not change:

- existing recovery file location
- existing profile/storage directory
- existing recovery JSON schema unless an additive backward-compatible field is absolutely required
- assignment semantics
- flight-session semantics
- history semantics
- PIREP semantics
- telemetry semantics

Existing recovery files must remain readable.

A user upgrading Sierra 4 must not lose an existing recoverable flight.


PART 3 — DEFINE REQUIRED SAVE GUARANTEES

Flight recovery persistence should provide the strongest practical guarantees available on the current Windows/filesystem architecture.

At minimum:

1. A successful Save leaves a complete readable recovery document.
2. A failed/interrupted Save must not leave the authoritative recovery file partially written.
3. Existing valid recovery should not be destroyed before replacement is safely available.
4. Temporary artifacts should be bounded and safely cleaned.
5. Concurrent or rapid saves must not corrupt recovery.
6. Transient external file contention should be handled safely where practical.
7. Retry behavior must be bounded.
8. Application shutdown must not hang indefinitely waiting for recovery persistence.
9. Failures must remain observable through diagnostics.
10. Recovery persistence must not silently report success when durability failed.


PART 4 — CONCURRENCY ANALYSIS

Determine whether FlightRecoveryStore.Save can currently execute concurrently or re-enter.

If application-level serialization is required, implement the smallest appropriate mechanism.

Do not introduce a global application lock unnecessarily.

If saves can be coalesced safely, distinguish:

- operational recovery state that must not be lost
- superseded intermediate recovery snapshots

Do not coalesce or discard state unless correctness is proven.

The final authoritative state must be persisted.


PART 5 — WINDOWS ATOMIC REPLACEMENT STRATEGY

Evaluate the appropriate Windows/.NET replacement strategy rather than blindly retaining File.Move(... overwrite:true).

Consider supported mechanisms such as:

- write temporary file in the same directory
- flush/close temporary file completely
- atomic replacement/rename semantics where available
- File.Replace where appropriate
- File.Move fallback where appropriate
- backup behavior if useful
- bounded transient retries

Choose based on actual .NET/Windows semantics and compatibility with Sierra 4's existing storage model.

Do not add a heavyweight persistence dependency for this problem.

Do not switch recovery to SQLite merely to avoid solving file replacement.


PART 6 — TRANSIENT RETRY POLICY

If evidence supports transient filesystem contention, implement a bounded retry policy.

Requirements:

- retry only errors reasonably classified as transient
- do not retry invalid paths, malformed state, permission configuration errors or other permanent failures indefinitely
- use a small bounded retry count/time budget
- use reasonable short backoff
- support cancellation/shutdown where appropriate
- preserve diagnostics
- record final failure if all attempts fail

Do not hide persistent filesystem problems behind endless retries.


PART 7 — DURABILITY

Review whether the temporary recovery file is actually closed/flushed before replacement.

Use appropriate flush/durability behavior for this small critical recovery document.

Do not make every telemetry sample perform unnecessarily expensive full-volume synchronization if not required.

Balance recovery reliability with flight-tracking performance and document the decision.


PART 8 — CRASH / INTERRUPTION SAFETY

Test or reason explicitly about interruption at these stages:

- before temp write
- during temp write
- after temp write but before replacement
- during replacement
- after replacement
- during cleanup

Define what file Sierra 4 will recover from in each relevant state.

If a temporary/backup recovery file may remain after a crash, determine whether startup should:

- ignore it
- clean it
- validate it
- use it only when the authoritative recovery file is missing/corrupt

Do not introduce automatic recovery from a temporary artifact unless its integrity and precedence are clearly defined.


PART 9 — FILE INTEGRITY

Where practical, ensure recovery reads reject incomplete/corrupt JSON rather than interpreting partial state as valid flight truth.

Preserve compatibility with existing valid recovery files.

Do not redesign the format unless necessary.


PART 10 — STRESS REGRESSION

Create focused automated stress coverage.

The previous standalone probe reproduced approximately 3 failures / 500 replacements.

After the fix, run a substantially larger bounded replacement stress test.

Target at least:

- 5,000 sequential replacements

and where appropriate:

- rapid replacement
- concurrent save attempts
- save/read overlap
- cleanup/recreation
- simulated transient lock/contention
- application shutdown/disposal interaction

Use temporary isolated test directories.

Do not modify the user's actual recovery/profile files.


PART 11 — TRANSIENT LOCK INJECTION

Where feasible, create deterministic tests that temporarily prevent replacement/access and verify:

- bounded retry succeeds when contention clears
- authoritative existing recovery remains readable during failed attempts
- permanent failure surfaces correctly
- no infinite retry
- no corrupt authoritative file
- temporary files are handled correctly

Prefer deterministic injected/file-abstraction tests over relying solely on antivirus or random OS timing.
