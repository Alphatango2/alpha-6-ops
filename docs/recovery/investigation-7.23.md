# Recovery replacement investigation (before production changes)

Starting commit: 8ab65cc. Runtime .NET 10.0.11, Windows 10 build 19045, local C: NTFS reports healthy. Repository owner is the current user. Probe files carry Archive, not ReadOnly; creation and almost all replacements succeed in the same directories. This is not evidence of a permanently unwritable directory.

The coordinator saves at the end of each telemetry observation, on individual tracking events, gate updates and schedule corrections. Multiple saves within one observation are sequential. Commands and simulator callbacks use the same verified runtime dispatcher. Shutdown/disconnect finalize the journal; they do not introduce a second recovery writer. Constructor restoration loads once. Assignment acceptance, clearing and successful PIREP closeout delete recovery on that dispatcher. There is no recovery watcher or other production writer found in repository search. Diagnostics use isolated coordinator directories; overlapping test stores could nevertheless collide if given the same directory.

Old Save uses WriteAllText to a fixed `.tmp`, which closes its handle, then a single File.Move(overwrite). Load uses ReadAllText, closing its read handle; that read does not share delete. Delete removes the authoritative file and fixed temp. There is no lock inside the store and no retry. Thus direct concurrent callers can race on the temp, readers can obstruct renames, and transient external handles can fail an otherwise valid save. There is no evidence that the normal coordinator concurrently calls this store.

Independent raw probe: 5,000 same-directory Move replacements failed five times; 5,000 Replace calls failed 27 times. Every failure recovered after 10 ms. Target and temp were still present at each observed failure, target attributes Archive. Move failures were AccessDenied; Replace included unable-to-remove-replaced. No app, simulator, renderer or test reader ran in those probe loops. This extends 7.22's independent 3/500 probe and establishes a transient replacement mode independently of browser contention. Lock ownership was not captured: antivirus, indexer or another filter/observer are possible, not proven causes.

Three tests fail against the old implementation: releasing a destination handle after 30 ms cannot rescue its single attempt; permanent-lock failure leaves temp behind; syntactically valid JSON missing required recovery fields is accepted.

Classification: **C/D/G** — characterized Windows replacement failure, possible external transient holder, exact actor unresolved. **A/B** are defensible store-level race risks demonstrated by direct calls, not the proven cause of normal telemetry failure. **E** accelerated tests increase replacement frequency, but standalone and classic runs rule out the Map V2 test harness as the sole cause. No evidence of damaged NTFS or persistent profile permissions (**F**).

The [.NET Windows implementation](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/IO/FileSystem.Windows.cs) delegates replacement to Windows. [MoveFileEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) supports replacing the destination. Same-directory staging avoids cross-volume copy/delete. [ReplaceFile](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) documents additional partial-failure outcomes, so changing APIs alone would not establish a safer contract. The fix will retain rename, add a bounded retry, serialize the store, flush staged data and keep only the authoritative name eligible for restoration.

No AV exclusions, permission changes, source-profile changes or suppressed error reports were used.
