# Frozen responsiveness policy — 7.24A.1 policy 2, tooling freeze 3

This is a **new** acceptance policy for the forthcoming 7.24A.1 readiness run. Historical 7.24A remains **NOT READY**, including its genuine 100.0243 ms failure under the original every-window p95 <100 ms rule. This document, the JSON limits and evaluators are hashed and timestamped before the final run. No tuning is permitted against final results.

## Evidence used before choosing the policy

The retained hour contains 47 steady visible windows, median window p95 47.3279 ms, with one at 100.0243 ms. Its p99 and maximum were 153.8838 and 250.563 ms. No causative production defect is established by those aggregates. The surrounding minimize/restore sequence remains a specific validation concern.

New fixed-order characterization: six fresh processes, 15-second warmup then three measured minutes each, six contiguous 30-second windows per trial. Full/light/light/full/full/light order; 36 windows total. Same production composition renderer, Operations workspace, independent 1.1 Hz current-flight input, production clock, actual durable recovery saves and unchanged presentation handlers. The constructor requested 1920×1080 but production startup fitting expands the window to **3440×1400** on this monitor; all six saved end-of-run preferences confirm that size. Characterization did not record per-window actual size, so it is not falsely described as a verified 1920×1080 run. Both modes retain passive activity timings, a 20 ms Input heartbeat, raw timing data and an independent bounded 100 ms Input-priority queue probe. Only diagnostic process/resource collection changes, from every five seconds to every 30 seconds.

Full sampling: 18 windows, median/max window p95 **57.6480/73.9427 ms**. Light: 18, **72.5256/91.8188 ms**. Neither mode exceeded 100 ms. Light collection reduced measured resource-collection work from approximately **1,364 to 246 ms** over nine measured minutes (about 82%), yet its median p95 was higher. Presentation p95 medians were approximately **24.43/24.05 ms**. These ordered repetitions do not establish a causal speed penalty from light sampling, but they do not support blaming resource diagnostics for the original miss. We retain both modes in acceptance; no subtraction of measured diagnostic time from heartbeat results is allowed.

## Required final evidence

- Two fresh processes, one per instrumentation mode, **five measured minutes each**, with 15-second warmups. At least **20 complete 30-second windows** and 500 heartbeat / 200 independent queue samples per window. At least 20 measured production presentation and recovery operations per window. All requested windows included; no cherry-picking. Window validity is 29–32 seconds to detect collection gaps.
- Raw samples must agree with reported quantiles and counts. Window indexes must be complete and ordered. Same visible renderer epoch throughout each trial. Active production clock; complete independent input at ≥1 Hz; one simulator source start; clean recovery and report guard; browser disposal within ten seconds.
- Every primary window must record the actual **3440×1400 DIP** viewport and production composition host. At the observed 96-DPI scale this equals pixels. This is a same-machine workload constraint, not certification of other monitors.
- **Median of window p95 values <80 ms in each mode.** The pooled nearest-rank 95th percentile of window p95 values must remain **<100 ms**. This preserves the original 100 ms target for at least 95% of windows and creates a separate central-tendency requirement with headroom.
- At most **5% of windows may exceed 100 ms**, none consecutively within a trial, and **no window p95 may exceed 120 ms**. With the planned 20 windows this permits at most one isolated exceedance. The 20 ms allowance is one nominal diagnostic heartbeat period, not a microsecond adjustment around the historical result.
- **Every window p99 <250 ms and maximum heartbeat interval <500 ms.** These are elapsed heartbeat intervals including the nominal timer interval, not estimated input-to-pixel latency. Sustained poor responsiveness or a large isolated stall must fail even if the median is good.
- Window closure captures unfinished heartbeat and Input-probe ages **before yielding**, applies the same 500 ms limits to those ages, drains Input work, and stops/drains the final probe producer before final evidence closes. Missing boundary measurements fail. A deliberately injected 600 ms UI stall verifies that a callback waiting across a window boundary cannot disappear from acceptance evidence. This fixes diagnostic censoring; no production behavior or numerical budget changes.
- **Every independent Input queue p95 <100 ms and maximum <500 ms.** No more than 15 skipped probe attempts per window (5% of nominal 300 attempts); only the probe is bounded, never authoritative input. Report skipped counts explicitly.
- Keep bridge end-to-end ACK p95 <500 ms and renderer start <5 s. Bridge timing distributions remain epoch-cumulative and are labeled as such; the independent queue probe is reset each window.
- A fresh **six-minute bounded full-flight/lifecycle run** must retain all ≥395 inputs, reach OUT/OFF/ON/IN and durable PIREP, exercise recovery retries, navigation, a real browser stall, minimize/restore, and clean final disposal/report guard. At least four complete steady visible supplemental windows must satisfy the same 120 ms p95 cap, 250 ms p99 and 500 ms maximum safeguards, with ≥500 samples and no resource-sampling errors. This specifically covers the steady period after minimize/restore. It supplements, rather than dilutes, the primary 20-window percentage rules.
- All affected Map V2/performance/recovery checks and baseline verification must pass. Operational production source must remain unchanged; if a production fix becomes necessary the full Sierra 4 suite is required and this measurement-only plan must be revisited.

## Why this is defensible, and its limits

The original single worst-window rule makes a pass depend on the number of observed windows and a very small boundary crossing, without distinguishing a brief tail event from a sustained problem. The new rule adds required duration/sample coverage, a per-mode central budget, a window-tail budget, a small capped isolated allowance, a consecutive-window rejection, direct queue evidence and maximum-stall safeguards. It is an explicit engineering acceptance policy for progression to native pilot validation, not a statistical proof of an underlying 5% population rate or a guarantee for all Windows systems. Windows from one machine are correlated; zero exceedances in 36 windows does not establish long-run tail probability. The stricter maximum-stall requirement is new; it was not silently applied to or used to rewrite historical 7.24A.

Microsoft documents that [DispatcherTimer execution depends on the Dispatcher queue and other work](https://learn.microsoft.com/en-us/dotnet/api/system.windows.threading.dispatchertimer). This supports measuring distributions, but supplies **no universal 100/120/250/500 ms SLA**. Those budgets are explicit product choices, grounded in the observed normal range and the need to reject sustained stalls. High-resolution timing remains valid; no rounding or claimed clock inaccuracy is used.

The unchanged production code, retained successful hour of full-flight/recovery/lifecycle coverage, 18 fresh measured characterization minutes, ten final steady minutes and six final lifecycle minutes make another full-hour repetition unnecessary for this narrow policy investigation. Native MSFS, real input-to-pixel latency, other GPUs/loads/monitors and long-term tail rates remain unverified. Map V2 stays opt-in and classic remains default. This policy authorizes no 7.24B work by itself.

## Pre-freeze review

Independent review found the boundary-censoring risk above. Three new evaluator cases initially failed (crossing heartbeat, crossing queue probe, missing boundary), then passed after fail-closed enforcement; all 26 policy contracts pass. The real UI boundary diagnostic passes seven checks including original process ownership, pending heartbeat/probe age and drained completion. Characterization measurements remain retained: the observed terminal heartbeat gaps were 16.6–62.1 ms and queue gaps 16.6–109.6 ms, with no demonstrated concealed >500 ms stall. Raw-output serialization gaps totaled approximately 15–18 ms per trial (largest 8.68 ms), and every final window retained 33 recovery operations. Those exploratory trials are not substituted for the corrected final acceptance run.

The first existing accelerated contention regression also recorded a 537.7024 ms maximum (control 325.2277 ms), failing its separate unchanged <500 ms/relative-baseline gate while all flight-state hashes matched. That attempt remains failed. The new steady-window policy does not override this regression or excuse it as diagnostic overhead; its repeatability and final affected-suite result must be reported separately.

Revision 2 supersedes the initial stored freeze **before any final acceptance trial began**. It corrects the viewport description and requires actual dimensions in final evidence. A changed-viewport fixture first failed and then passes with fail-closed validation (27 evaluator cases). **All numerical latency, duration, sample, input and stall limits are unchanged.** The initial freeze is retained as `policy-freeze-initial-superseded.json`; no final result was available when this metadata correction was made.

## Additional characterization before final tooling freeze

The existing performance profile sequence retained all functional assertions (51/51), but reproduced composition-host heartbeat p95 of **827.3045 ms full, 812.1076 ms light, 816.4496 ms light-repeat**, with queue p95 above one second. A native-host diagnostic control was 45.5981 ms. Those profiles stop the production dashboard clock and use UI-paced inputs, unlike the fresh independent-feed trials. Their latency cannot be attributed to a particular production handler, dismissed as resource collection, or claimed to prove normal flights stall identically. These unresolved waits remain a readiness blocker even if the primary final policy assessment passes.

Two additional fresh three-minute observations kept the full production clock, telemetry, presentation and recovery work. With the extra Input probe removed but 50 ms Normal monitoring still active, six windows had median/max p95 **65.1912/71.0692 ms**, maximum heartbeat 367.4245 ms. Removing both the extra probe and frequent polling produced median/max p95 **75.3719/100.1097 ms**, maximum heartbeat 354.2482 ms: one of six windows exceeded 100 by 0.1097 ms. Both retained 215/215 inputs. These are characterization arms, not final acceptance and not sufficient to establish a causal observer effect. They show that active monitoring must not be treated as an exact production responsiveness benchmark. No time is subtracted from reported latency.

Tooling freeze 3 stores the final diagnostic binary source after adding these passive modes. Revision 2's manifest is retained as `policy-freeze-viewport-superseded.json`. **The JSON policy, evaluator, latency limits, final sequence and required coverage are unchanged. No final trial had begun.** The final two primary trials deliberately keep their preselected full/light instrumentation; the passive and broader-profile evidence must still inform the separate overall readiness decision. A successful numerical assessment alone does not resolve the observed scheduling symptom.
