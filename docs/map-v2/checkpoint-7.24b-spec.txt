CHECKPOINT 7.24B — INSTALLED NATIVE MSFS PILOT VALIDATION

PURPOSE

The automated 7.24A investigation series is complete.

Historical decisions remain:

7.24A:
NOT READY

7.24A.1:
NOT READY

7.24A.2:
NOT READY under the automated/root-cause prerequisite.

However, 7.24A.2 established that:

- the frozen final numerical responsiveness assessment passed
- authoritative flight processing remained intact
- Map V2 remains presentation-only
- recovery remained intact
- PIREP behavior remained intact
- lifecycle/disposal remained intact
- the unresolved issue is intermittent WPF/WebView2CompositionControl scheduling delay
- no safely remediable production defect was identified
- no production fix was justified
- Map V2 remains opt-in
- classic map remains default/fallback

Checkpoint 7.24B is therefore authorized as a CONTROLLED INSTALLED PILOT VALIDATION.

This is NOT approval to make Map V2 default.

This checkpoint exists to determine how Sierra 4 behaves when:

- installed normally
- connected to real Microsoft Flight Simulator
- receiving real SimConnect data
- operated by a real user
- used during an actual flight
- using actual physical mouse/keyboard/display/DPI behavior

This checkpoint should close as much of the native/manual validation gap as possible.

DO NOT attempt to solve the Composition scheduling issue during the validation flight.

FIRST CAPTURE REAL-WORLD EVIDENCE.


============================================================
PART 1 — FREEZE AND ARCHIVE THE VALIDATION BUILD
============================================================

Before building or installing anything:

1. Record the exact source commit.
2. Archive the source manifest.
3. Archive the exact production DLL/executable binaries used for validation.
4. Record SHA-256 hashes for:
   - executable
   - primary application DLL
   - installer
   - portable ZIP if produced
   - Map V2 browser assets
5. Record configuration relevant to Map V2.
6. Record the exact validation version/build identifier.

Do this BEFORE subsequent rebuilds.

This explicitly addresses the historical binary-retention limitation identified during 7.24A.2.

The validation build must be reproducible and identifiable after testing.

PART 8 — NATIVE MSFS CONNECTION LIFECYCLE
============================================================

Launch Microsoft Flight Simulator normally.

Test the previously unavailable native gate:

NATIVE_CONNECTION_LIFECYCLE

Validate:

1. Sierra 4 initially disconnected.
2. Connect Sierra 4 to the running simulator.
3. Native SimConnect connection succeeds.
4. Real telemetry begins arriving.
5. Sierra 4 reports the correct connection state.

- successful native connection

- stale callback

- failure

PART 12 — HUMAN-PERCEIVED RESPONSIVENESS OBSERVATION
============================================================

This is a major objective of 7.24B.

During the flight, periodically perform:

- map pan
- zoom
- aircraft selection
- Follow/Unfollow
- shell navigation
- Operations → another workspace → Operations
- resize where safe
- minimize/restore where safe

Record any user-visible responsiveness event approximately as:

A. NO NOTICEABLE HITCH

B. MINOR HITCH
   visible but not disruptive

C. MAJOR HITCH
   obvious pause / roughly 0.5–1 second

D. SEVERE FREEZE
   roughly 1+ second or clearly disruptive

For each noticeable event record where practical:

- approximate time
- flight phase
- action being performed
- whether Map V2 was visible
- whether map was moving
- whether surrounding WPF UI also froze
- whether flight telemetry continued
- whether the application recovered automatically

Do not claim a Dispatcher heartbeat measurement equals a user-visible freeze.

Do not dismiss a user-visible freeze merely because flight telemetry remains intact.

============================================================
PART 19 — MAP V2 DECISION
============================================================

At the end of 7.24B classify Map V2 as:

A. CANDIDATE FOR DEFAULT

B. REMAIN OPT-IN

C. DISABLE FOR NORMAL USE

Do NOT automatically change the default setting during this checkpoint.

CANDIDATE FOR DEFAULT requires:

- native connection lifecycle passes
- native reconnect passes
- physical map input is acceptable
- actual DPI/window behavior is acceptable
- real flight completes correctly
- recovery validation passes
- PIREP/history persist correctly
- no serious user-visible Map V2 freeze occurs
- no critical unexpected reports occur
- operational flight truth remains unaffected

If user-visible freezes occur but flight truth remains intact:

REMAIN OPT-IN.

If Map V2 destabilizes the application or flight workflow:

DISABLE FOR NORMAL USE.

Changing the actual default requires a separate explicit decision after reviewing this report.
