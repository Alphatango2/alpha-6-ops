## Input root cause

The full test raised a WPF `MouseDown` without first supplying a coordinate-bearing `MouseMove`. The pinned WebView2 SDK (1.0.4191.47) forwards button events using `_mouselocation`, populated by its mouse-move handler. Resizing/scaling the Operations window can leave that cached position outside the current browser viewport. The browser correctly receives no in-document `mousedown` for that position.

The unchanged test with added observation reproduced failure at cached **(777, 605)** against a **1283 × 316** viewport. It exhausted the original 1,500 ms budget without a DOM event. The SDK IL was already preserved in `work/checkpoint-7.24b-physical-input/sdk-input-il.txt`; inspection establishes that `OnMouseDown` reads the cached point rather than `MouseButtonEventArgs.GetPosition`.

Controlled A/B/A/B, with the same initialized renderer and no production change:

| SDK press coordinate | Browser acknowledgment |
|---|---|
| (777, 605), outside | FAIL |
| (777, 158), inside | PASS |
| (777, 605), outside | FAIL |
| (777, 158), inside | PASS |

`cache-abab` establishes causality by changing only the cached input coordinate. `wpf-move-abab` independently reproduces the same result using actual routed WPF mouse moves instead of writing SDK state. The earlier position-only probe passed outside because it had not updated the SDK cache; that result was insufficient to rule out coordinate dependence.

Opacity was a confounding observation, not the input cause: the corrected full run receives the expected trusted event even when the restored renderer is still concealed pending its completed first paint. Existing first-paint/restoration assertions remain in the suite and are not bypassed.

## Diagnostic correction

`SyntheticMapPointer.Move` supplies a coordinate-bearing mouse input report through WPF's input staging pipeline. This is the same input-report seam used by [WPF MouseDevice.Synchronize](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/PresentationCore/System/Windows/Input/MouseDevice.cs). WPF's public mouse position is itself cached; merely moving a test window or calling Synchronize without a new coordinate report did not correct the full-workspace precondition. Those unsuccessful diagnostic approaches remain recorded.

The full check now establishes an in-bounds pointer, sends a routed move/down/up sequence, restores the prior synthetic position in `finally`, and verifies a trusted in-bounds browser event. It does not move the OS cursor, write WebView2 private state, inject a CDP mouse click, change application focus handling, or alter the original 1,500 ms limit. Two additional assertions check the precondition and received event position/trust. WPF's internal input-report types are accessed only in this explicit diagnostic helper and fail closed if the seam changes.

A separate diagnostic launcher supplied that same missing move before the original test's zero-timestamp synthetic press while executing **byte-identical frozen T2 application binaries** from a disposable copy. The original full suite passed **197/197**. The launcher leaves the frozen package and application methods untouched; its results are separate from rebuilt-source verification. This supports a test-input defect rather than a T2 production input regression.
