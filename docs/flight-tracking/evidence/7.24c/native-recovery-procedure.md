# Native active-flight recovery gate (pending)

The automated process tests use fixed synthetic telemetry and an injected simulator source. They exercise the production coordinator, dispatcher callback path, JSON recovery, SQLite history and PIREP closeout. They do not exercise SimConnect, an installed binary, or the physical simulator's reconnection behavior.

Run only after the corrected build is frozen and its installed payload identity is verified. Use a controlled short validation flight and preserve the original source logs. Record this separately from JST776, historical reference flights, and synthetic replay totals.

1. Record the frozen build identifier/hash, simulator aircraft/registration, accepted flight number, airports and dated simulator schedule. Keep MSFS running throughout the OPS restart. Include the normal no-simulator-flight-plan case when the dispatch assignment was verified at its departure airport.
2. Start at the departure gate, connect once, then fly until both OUT and OFF have been observed. Record their exact dated simulator times, the current phase and the detailed event count. Record the original durable history row ID from a consistent read-only database backup. Do not edit the active profile.
3. At a stable airborne point, record simulator UTC/position and OPS assignment/route/session context. Exit OPS normally while leaving the same MSFS flight active. Do not reload the flight, reposition the aircraft, change aircraft, rewind simulator time, or replace the dispatch assignment.
4. Reopen the frozen OPS build. Before reconnecting, verify the same assignment, route, OUT/OFF times, event history and Airborne phase are restored; current live data must remain unavailable until a new connection supplies it.
5. Connect to the existing MSFS flight. Record native connection evidence and the first resumed sample. Verify the assignment still identifies the same flight, OUT/OFF remain unchanged, and unchanged engine states do not produce a second running/start event. No second operational history row or fresh OUT/OFF may appear. Distinct diagnostic connection journals are expected and are not duplicate flights.
6. Continue to the destination. Land once, taxi in and complete the normal automatic or explicitly pilot-confirmed IN procedure. Record exact ON and IN times and all four lifecycle milestones in order. Confirm PIREP eligibility.
7. Submit the PIREP once. Verify the assignment and active recovery are cleared, and the local history shows the original flight ID with Complete phase and one PIREP containing the four recorded actuals. Repeated submission must not produce another PIREP.
8. Exit and reopen OPS again. From a consistent read-only backup, verify one completed history row for this run, one PIREP, contiguous appended event sequences, unchanged pre-restart event payloads/times, and no duplicate OUT/OFF/ON/IN or steady-state engine events. Check that old diagnostic journals remain unchanged after their connection has ended.
9. Inspect new crash/error reports relative to the recorded baseline. A graceful exit/restart should not create a previous-unclean-exit report or persistence error. Preserve every unexpected report and treat it as a failed gate pending investigation.

If an abrupt termination scenario is also authorized for the dedicated test flight, repeat separately at a fully saved airborne checkpoint. Expect one previous-unclean-exit report. Do not represent that expected report as a persistence failure, and do not allow other unexpected reports. The synthetic harness already covers both clean exit and deliberate process kill; native abrupt termination has not been performed here.

Evidence required to close the native gate: frozen installed identity; exact restart/reconnect timestamps; native connection result; before/after assignment, milestone and event snapshots; unchanged original history ID; final persisted PIREP payload/count; post-restart durable history; source-hash manifest; unexpected-report audit. A normal completed flight or passing synthetic test alone is insufficient.
