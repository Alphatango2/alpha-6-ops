============================================================
OBJECTIVE
============================================================

Implement a safe completion-specific terminal-shutdown architecture that
separates:

1. PILOT INTENT / OPERATIONAL TERMINAL SHUTDOWN

from

2. MECHANICAL ENGINE SPOOL-DOWN STATE

Do NOT weaken or replace the existing generic mechanical engine classifier.

The existing Running / Stopping / Off classification remains authoritative
for mechanical engine state, telemetry, event recording and other systems.

TerminalShutdownEvidence is a separate concept used only where appropriate
for determining terminal flight completion.

============================================================
PART 1 — AIRCRAFT-CAPABILITY ARCHITECTURE
============================================================

Do NOT hard-code Fenix-specific conditions throughout
FlightSessionCoordinator or generic lifecycle code.

Create an extensible aircraft shutdown-intent capability boundary.

The architecture should allow S4 to ask conceptually:

“Can this aircraft integration positively establish intentional terminal
shutdown for all required engines?”

Normalize aircraft-specific evidence into a generic result such as:

TerminalShutdownEvidence

with information equivalent to:

- capability/support level
- expected engine count
- observed engine coverage
- per-engine shutdown intent
- per-engine combustion state
- signal freshness
- signal validity
- contradictory evidence
- overall terminal-shutdown status

Exact names/types are an implementation decision.

The lifecycle coordinator should consume normalized evidence rather than
know Fenix LVar names.

============================================================
PART 2 — CAPABILITY LEVELS
============================================================

Support an extensible model equivalent to:

FULL / ENHANCED

Positive shutdown intent can be established for all required engines.
Automatic terminal completion may use this evidence.

LIMITED / UNSUPPORTED

Shutdown intent cannot be positively established.
Do not use combustion OFF alone as automatic authority.
Use guarded manual Block In fallback.

INVALID / CONTRADICTORY

Required evidence is missing, stale or contradictory.
Neither automatic completion nor unsafe manual completion should occur
until sufficient valid evidence exists.

Do not overfit the names if the existing architecture suggests better
terminology.

============================================================
PART 3 — FIRST ADAPTER: FENIX A321 IAE
============================================================

Implement the Fenix A321 IAE as the first validated enhanced shutdown-intent
integration using the evidence from the native capture.

The validated candidate master signals are:

L:S_ENG_MASTER_1
L:S_ENG_MASTER_2

Use the native capture to establish polarity and expected behavior.

Combine shutdown intent with combustion evidence.

Do NOT use master OFF alone.

For automatic terminal-shutdown evidence, require all expected engines to
have:

- positively verified master/cutoff OFF intent
- combustion absent
- fresh/valid evidence
- no contradictory operating evidence

Mechanical N1/N2/fuel-flow decay may continue after terminal shutdown has
been established.

Do NOT alter the generic engine classifier's fuel-flow/N1/N2 thresholds.

============================================================
PART 4 — TERMINAL COMPLETION ELIGIBILITY
============================================================

Automatic terminal shutdown must NOT by itself produce IN.

The flight must also satisfy the complete terminal-arrival predicate.

At minimum evaluate:

- ON milestone already recorded
- aircraft on ground
- correct destination proximity
- stationary / valid low-groundspeed condition
- parking brake SET
- complete expected engine coverage
- valid terminal shutdown evidence
- fresh/noncontradictory telemetry
- no active pause/slew/disconnect invalidation
- stable confirmation interval

Use existing lifecycle semantics where appropriate.

Do not create a second conflicting definition of destination arrival.

Preserve exactly-once IN behavior.

============================================================
PART 5 — INTERRUPTION / RESET RULES
============================================================

Pending terminal completion must reset or become invalid when appropriate,
including:

- aircraft movement
- parking brake release
- engine master returned ON
- combustion relight
- go-around/repositioning where applicable
- pause/slew invalidation
- simulator disconnect
- stale telemetry
- missing engine coverage
- contradictory engine evidence

Reconnect/recovery must require fresh valid evidence before terminal
completion resumes.

Do not allow stale pre-disconnect shutdown evidence to immediately complete
a recovered flight.

============================================================
PART 6 — HARDEN MANUAL BLOCK IN
============================================================

The prior analysis found that the current manual Block In behavior:

- can permit an off-destination override
- does not recheck the complete eligibility predicate

Correct this.

Create or consolidate a shared authoritative Block-In eligibility policy so
automatic terminal completion and manual confirmation agree on the safety
requirements that should be common.

Manual Block In exists as a fallback for aircraft where positive shutdown
intent is unavailable.

It must still require appropriate evidence such as:

- ON recorded
- on ground
- valid destination proximity
- stationary
- parking condition / required stable interval
- valid current session
- fresh enough telemetry

Do NOT permit manual Block In to become a generic bypass for lifecycle
requirements.

If there is a legitimate existing recovery/emergency use case for an
off-destination override, preserve it only as a separately explicit and
appropriately guarded mechanism rather than silently treating it as normal
Block In.

============================================================
PART 7 — EXPECTED USER EXPERIENCE
============================================================

For an enhanced-supported aircraft such as the validated Fenix:

ON
→ taxi to destination parking
→ stop
→ parking brake SET
→ all required engine masters OFF
→ combustion OFF
→ short stable confirmation
→ IN / Complete
→ PIREP eligible

S4 should NOT wait for residual turbine fuel flow to fall <=1 lb/hour merely
to establish operational terminal shutdown.

The mechanical engine state may continue to report Stopping while the flight
is operationally Complete.

This is intentional.

For unsupported aircraft:

ON
→ destination parking conditions satisfied
→ automatic shutdown intent unavailable
→ guarded Confirm Block In becomes available

Do not implement premium UI styling for this fallback during 7.24C.

============================================================
PART 8 — CROSS-AIRCRAFT EXTENSIBILITY
============================================================

Fenix is the FIRST validated adapter, not the definition of the feature.

Do not attempt to implement every aircraft now.

The architecture must allow future integrations for aircraft such as:

- PMDG
- iniBuilds
- other advanced third-party aircraft
- generic MSFS aircraft where reliable standard signals exist

without modifying the core completion state machine for each aircraft.

Document how another aircraft shutdown-intent adapter would be added and
what native evidence would be required to promote it to enhanced/full
support.

Consider maintaining an aircraft capability/compatibility matrix in future,
but do not build unnecessary UI for it now.
