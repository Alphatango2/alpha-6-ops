============================================================
OBJECTIVE
============================================================

Determine exactly what the heartbeat measures, why it occasionally exceeds
the existing acceptance limit, and whether the cause is:

A. a production scheduling defect
B. a deterministic interaction with S4 workload
C. WPF/dispatcher behavior that S4 can safely improve
D. native OS/runtime scheduling variance
E. measurement/test methodology
F. another measurable cause

Do not classify the result until evidence supports it.

============================================================
PHASE 1 — DEFINE THE HEARTBEAT
============================================================

Document precisely:

- where the heartbeat is scheduled
- DispatcherPriority used
- expected cadence
- timestamp source
- how latency is calculated
- what the relative comparison limit represents
- why that limit was originally selected
- what production behavior the heartbeat is intended to protect
- whether the heartbeat corresponds to a real user-visible interaction or
  is a synthetic scheduling sentinel

Trace:

heartbeat scheduled
→ dispatcher queue
→ competing dispatcher work
→ callback begins
→ latency recorded

Identify everything that can legitimately execute ahead of it.

============================================================
PHASE 2 — CORRELATE FAILURES
============================================================

For every preserved heartbeat failure, correlate the timing against:

- pointer/input activity
- WPF rendering
- composition
- map snapshot delivery
- WebView2 messages
- browser ACKs
- telemetry processing
- route projection
- serialization
- workspace navigation
- garbage collection
- file/database activity
- logging
- test harness activity
- process/thread scheduling
- CPU utilization where evidence exists

Determine whether the 400–513 ms waits correspond to any specific S4
operation.

Do not infer causation from temporal proximity alone.

============================================================
PHASE 3 — MEASURE DISPATCHER QUEUE BEHAVIOR
============================================================

Add diagnostic instrumentation only if required.

We need to know whether a failing heartbeat is:

1. waiting behind one long callback

2. waiting behind many individually short higher-priority callbacks

3. descheduled by the OS/runtime

4. delayed by rendering/composition behavior

5. affected by test instrumentation itself

6. another mechanism

Measure callback durations and queue/scheduling behavior sufficiently to
distinguish these cases.

Do not change production scheduling yet.

- subsequent no-hitch/no-flicker observations

============================================================
PHASE 6 — DECISION
============================================================

After evidence collection, classify the heartbeat instability as one of:

PRODUCTION DEFECT

A specific S4 scheduling mechanism causes unacceptable starvation.

If so:
- identify root cause
- propose smallest safe correction
- implement only after root cause is established
- preserve telemetry fidelity and current map scheduling semantics

TEST/METRIC DEFECT

The heartbeat or its calculation does not validly measure the production
behavior it claims to protect.

If so:
- explain exactly why
- propose a corrected metric/test based on product behavior
- do NOT simply loosen its threshold

ENVIRONMENTAL/NATIVE VARIANCE

The measurement is valid, but observed excursions originate outside S4's
controllable scheduling behavior and do not correlate with a production
responsiveness failure.

If so:
- provide strong evidence
- do not silently delete the gate
- recommend how this should be represented in future acceptance testing

UNRESOLVED

Evidence is insufficient.

If unresolved, 7.24C remains NO-GO.
