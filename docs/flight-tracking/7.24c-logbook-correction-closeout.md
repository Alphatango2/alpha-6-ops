## Root cause and correction

The old `PilotLogbookWorkspace.OperationalTimes` searched rendered event titles for OUT, OFF, ON and IN. OUT/ON/IN happened to be correct in JST500, but none of these four selectors guaranteed authoritative persisted actuals. OFF used the first title containing `Liftoff` or `Takeoff`, selecting takeoff roll at `20:07:15.8467025Z` instead of OFF at `20:07:33.8616943Z`: **18.0149918 seconds early**. This was not history corruption, a PIREP error, or changed flight-phase detection.

The view now passes the raw events for its selected `row.Id` to `PilotLogbookOperationalTimes`. For each field it prefers the persisted `pirep_submitted` payload's `actualOut`, `actualOff`, `actualOn`, or `actualIn`. The stored precision is retained; only the visible UTC format truncates to whole seconds.

Fallback is restricted and explicit:

1. A **present** authoritative field, including an explicit null, wrong type or invalid date, is authoritative. Unusable values display unknown; descriptive events cannot fabricate a value.
2. If that field is **absent** in an older record, use structured `phase` milestones and their simulator timestamps: `TaxiOut`, `Airborne`, `TaxiIn`, `Complete`.
3. If those are unavailable, support exact historical tracking milestone names: `Block-out / taxi out`, `Liftoff`, `Touchdown`, `Block-in / flight complete`. Takeoff roll, approximate taxi descriptions, engine shutdown and session-end text are excluded.
4. Use the first OUT/OFF and last ON/IN, matching the existing PIREP writer. Never substitute recording/computer time. Unparseable payloads provide no milestone evidence.

The existing FlyVirtual imported-history wording is unchanged. There are no history writes, SQL changes, database migrations, duration changes or new callsign joins. The event timeline continues to include takeoff roll and other useful details.
