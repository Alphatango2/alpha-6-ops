## Dashboard consumer analysis

`MainWindow.Dashboard.UpdateClock` reads current UTC at execution, renders wall-clock/local-time displays, refreshes local-weather presentation and calls `RefreshOperations`. Operations reads the current coordinator snapshot. Live `RuntimeChanged` also refreshes Operations, so tracking is not driven exclusively by the one-second timer.

This is a periodic current-state refresh, not an ordered stream of historical clock/weather states. A delayed tick should sample the newest state once; replaying every missed second would manufacture stale UI work. The existing timer/callback already has those semantics. No priority, interval, producer cadence or refresh algorithm was changed.

The clock can retain its previous displayed second while a callback is deferred. The earlier native **approximately 1.09 s ready wait** therefore matters to this consumer; it is not evidence of missing authoritative flight state. The new controlled test observes a 1.542 s callback interval and verifies current output after that delay, with no stale-state replay or operational mutation. It does **not** certify a strict one-second displayed-clock SLA or claim no stale pixel was ever visible between callbacks. There is no established tighter numerical/native product budget here, and no demonstrated defect justifying production optimization in this task. Physical T2 review remains responsible for visible freshness/hitch complaints.
