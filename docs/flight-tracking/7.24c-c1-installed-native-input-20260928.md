## Remaining scheduling finding

The physical result does **not** erase a separate map-data scheduling delay. A `WebMapRenderer.ApplyAsync` UI callback was posted at trace time **60,001.642 ms** and began at **64,282.469 ms**, a **4,280.827 ms** wait. Its runtime dispatcher priority was **Background (4)**, matching `WebMapRenderer.cs`'s production `Dispatcher.InvokeAsync` call. Several other map delivery callbacks waited over three seconds.

During that longest window:

- 3,748 WPF drag notifications continued; maximum message age was 16 ms.
- 1,026 `MediaContext.RenderMessageHandler` operations began.
- Four native telemetry observations completed, with arrival-to-processing delays of 0.434, 0.739, 0.431 and 0.348 ms.
- A queued Input-priority staging callback also waited 3,689.385 ms, despite continuing physical drag delivery. A queued Input sentinel is therefore not interchangeable with observed native pointer responsiveness.

This establishes delayed **map snapshot delivery to the browser**, while the user observed responsive pan and authoritative telemetry continued. It does not establish that the 4.28-second wait caused the previously reported visible hitch, nor that the current browser image was stale by precisely that duration. There are no browser snapshot/frame acknowledgments in this native trace. High-frequency pointer/render activity and lower-priority dispatch delay warrant a targeted scheduling comparison; this capture alone does not isolate every cause of that delay.

Raw timer posted-to-start intervals include intentional inactive timer waits and are not treated as scheduling latency. The analysis reports non-timer operations separately. No thresholds, production priorities, update cadence, operational code or map configuration were changed in this follow-up.
