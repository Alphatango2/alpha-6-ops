## Map scheduling

### Root cause of the 4.28-second wait

The delayed operation was the worker-to-WPF handoff in `WebMapRenderer.ApplyAsync`, before `Core.PostWebMessageAsJson`. It used `DispatcherPriority.Background` (4). C1's physical trace records posting at 60001.6423 ms and execution at 64282.4689 ms: **4280.8266 ms queued**, not 4.28 seconds spent executing map code.

During that interval, 3,748 WPF drag notifications, 1,026 Render-priority callbacks, and four Normal-priority telemetry callbacks continued. The user observed smooth panning. No single long managed callback, synchronous bridge post, projection, serialization, or GC pause explained that wait.

WPF treats Background and Input as background scheduling: they can wait for the native input/event/posted-message queue to clear. Render is in its foreground scheduling range. This explains how native mouse dispatch and higher-priority composition/telemetry can continue while a queued Background map post waits. The trace does not identify every native message or prove a GPU stall. See the [WPF dispatcher implementation](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/WindowsBase/System/Windows/Threading/Dispatcher.cs).

The independent real-renderer regression maintains render-priority pressure for 750 ms. Before correction, the bridge waited 777.0127 ms; a Render probe waited 0.6041 ms while Loaded waited 749.9857 ms. This establishes the scheduling boundary rather than attributing the problem to MapLibre frame rate.

### Pipeline and boundaries

| Stage | Existing execution and result |
|---|---|
| Telemetry arrival | Dedicated SimConnect worker; every reading enters the existing connection callback. No capture/source cadence change. |
| Tracking/recording | Normal-priority runtime dispatcher processes authoritative readings, milestones, journal/history/recovery, then publishes an immutable session snapshot. |
| Presentation offer | Operations offers a snapshot to the bounded map projection mailbox; continuity/generation checks run before coalescing. |
| Map generation | Worker projects the newest pending state at the existing 200 ms cadence. No Core flight computation is moved here. |
| Serialization | Renderer mailbox worker validates and serializes outside the WPF thread and outside its short ACK lock. |
| WPF dispatch | **Corrected:** only the pre-serialized WebView post uses Render priority (7), below authoritative Normal (9). No synchronous wait or bulk UI work is introduced. |
| WebView / MapLibre | Browser receives the message, applies snapshot sources/solar state, and ACKs. First-visible-paint readiness still waits for the required frame; the existing 3-second post-to-ACK timeout is unchanged. |
| Composition / input | Existing CompositionControl and MapLibre interaction semantics are unchanged. Native pointer delivery is distinct from an Input-priority synthetic dispatcher probe. |

The two latest-value mailboxes already bound work to one in-flight item and one newest pending item each. Locks protect short state exchanges, never await browser/dispatcher completion. Projection and bridge workers use asynchronous continuations; no new synchronization context or lock was introduced.

### Presentation semantics

All authoritative telemetry samples remain processed and recorded. Pending visual snapshots may supersede one another: if five positions arrive during a busy interval, the map should consume the newest pending complete snapshot, while an already in-flight snapshot may finish. It does not replay all five stale visual states sequentially. Coalescing is confined to presentation; telemetry journal, flight recorder, operational events, recovery, history and PIREP contracts are preserved. The map's visible trail remains a presentation history, not the authoritative flight archive.

In the corrected contention run: 395 samples were offered; projection coalesced 355 into 40 projections; the bridge coalesced six, acknowledged 34, and drained with no pending/rejected snapshot. Both arms still recorded **395 samples, 27 identical events and four identical milestones**, plus equivalent per-sample ETA/progress/PIREP eligibility, recovery, completed history and durable PIREP. Fifty authoritative samples were processed during the actual injected one-second JavaScript stall.

## Terminal shutdown

### Established JST776 finding

See `7.24c-engine-shutdown-pirep-analysis.md` for the complete timestamp reconstruction. Both combustion indications first became false at simulator **22:26:32.2787399Z**. Effective IN is **22:27:29.2802352Z**; Complete/eligibility is **22:27:33.2773437Z**. The respective delays are **57.0015 s** and approximately **60.9986 s**. No engine-master command timestamps were recorded. Residual reported fuel flow, not an extra PIREP timer, was the primary mechanical-classifier blocker. N1/N2 had already fallen below the classifier's bounds substantially earlier.

### Proposed completion-specific architecture — design only

Keep `EngineEvidenceTracker` for mechanical Running/Starting/Stopping/Off state, events and existing telemetry. Do not relax its oil, fuel-flow or spool rules to accelerate completion.

Introduce a separate immutable `TerminalShutdownEvidence` at the simulator boundary. It should carry aircraft/session/connection identity, source/capability revision, expected engine count, each engine's verified cutoff/master intent and combustion indication, receipt/simulator timestamps, coverage and validity reasons. Raw observation validity must be separate from the current `EngineDataValid`, which currently means all mechanical classifications are stable Off/Running and is false during legitimate spool-down.

A completion policy/monitor consumes this neutral evidence. Aircraft mapping belongs in a capability provider at the simulator boundary; no Fenix-name branches spread through `FlightSessionCoordinator`. Initially add only mappings justified by capture, not speculative aircraft adapters.

Candidate automatic terminal eligibility requires a recorded ON for this exact flight, TaxiIn/on-ground state, verified destination, stationary groundspeed, parking brake set, all expected engines positively commanded cutoff and combustion absent, fresh coherent observations, no pause/slew/identity/generation interruption. Reuse the existing three-second stable Complete confirmation as the proposed total confirmation interval; do not stack a second timer or change the mechanical classifier. IN retains its exactly-once transition and the existing exact completed-history identity / idempotent PIREP submission.

Invalidate pending confirmation on movement, brake release, relight, contradictory/missing expected signals, stale data, simulation-time discontinuity, pause, slew, disconnect or connection-generation change. Restart requires fresh evidence and a new confirmation interval, never a persisted partial timer. Residual N1/N2/oil/fuel flow alone must not veto a *verified* intentional cutoff; mechanical state remains independently visible. Failure or fuel starvation with masters still ON cannot satisfy cutoff intent.

### Capability model

| Capability/evidence | Proposed behavior |
|---|---|
| Full support, fresh consistent evidence | Automatic terminal intent is available only when **all** required masters/cutoffs and other terminal guards are satisfied. |
| Known limited/unsupported intent | No inference from combustion false or a default zero. Offer a guarded pilot confirmation when clearly parked at the destination. |
| Invalid/contradictory or transiently incomplete evidence | No automatic completion and no unsafe confirmation. A transient failure of previously supported signals must not silently downgrade to the permissive limited fallback. |

Represent provider support separately from dynamic validity so unsupported, missing, stale, and contradictory are not conflated. Capability is scoped to aircraft/variant/provider version. A successful SimVar registration or a stream of zeroes is not proof of support. Four-engine coverage must enumerate all four engines; never assume a twin-engine mask.

Historic replay/recovery compatibility needs explicit versioning when this policy is eventually implemented: the old nine journals lack command intent. Do not fabricate intent in those files or silently reinterpret their completed flights. Preserve legacy evidence/replay interpretation and specify which policy an active/new session uses before introducing a live authority change.

### Fenix signals and native capture

Installed package manifests report **Fenix 2.4.0.4720**. The shared cockpit XML identifies `S_ENG_MASTER_1` and `S_ENG_MASTER_2` at lines 3719/3723; its toggle-lift template directly reads/writes the matching LVars. The template's tooltip is action-dependent; no numeric ON/OFF polarity is assumed. Paths and SHA-256 hashes are retained in the evidence directory.

The [Fenix hardware-integration guide](https://support.fenixsim.com/hc/en-us/articles/12466468901135-Example-of-How-to-Bind-Switches-Knobs-and-Buttons-on-FenixSim-Aircraft-to-External-Hardware) identifies this installed XML as the source of control variables. The [official SimConnect data-definition API](https://docs.flightsimulator.com/msfs2024/html/6_Programming_APIs/SimConnect/API_Reference/Events_And_Data/SimConnect_AddToDataDefinition.htm) supports LVar reads through the existing native interface; no new WASM bridge is necessary to try these candidates.

| Candidate | Use in this investigation |
|---|---|
| `L:S_ENG_MASTER_1`, `L:S_ENG_MASTER_2` | Most direct intent candidates. Must prove native accessibility, polarity, per-engine independence and correspondence with cockpit actions. |
| `GENERAL ENG FUEL VALVE:1/2` | Correlate with master commands; valve state alone may reflect system/failure behavior and is not accepted as intent. |
| `GENERAL ENG COMBUSTION:1/2` | Raw running/combustion corroboration, not intent. |
| `TURB ENG FUEL FLOW PPH`, `TURB ENG N1/N2`, starter, oil pressure | Preserve mechanical transition/tail evidence; no decay-to-zero authority for the proposed fast path. |
| `GENERAL ENG FAILED:1/2` | Unvalidated failure-status candidate; unsupported replies must remain unavailable. |
| Engine count/title, sim UTC, pause/slew, ground/brake/speed/position | Establish capture identity, coverage and validity context. |

Generic engine SimVars are documented in the [MSFS SDK](https://docs.flightsimulator.com/msfs2024/retail/programming-apis/simvars/aircraft-simvars/aircraft-engine-variables/); documentation alone does not establish Fenix fidelity. There is no existing recorded master/cutoff evidence in JST776. **Can automatic authority safely be enabled now? NO. Native parked capture required: YES.**

The standalone `scripts/capture_fenix_shutdown.py` reads candidates at one-second intervals, records every raw response, field registration/HRESULT/exception, wall/simulator time and package/source hashes. It never writes simulator controls, opens Sierra, modifies a profile, or automatically reconnects. Parser/field isolation tests pass; actual native behavior remains unverified. A zero value remains unvalidated. Separate definitions prevent one unsupported optional variable from invalidating all returned fields. Per-field receipt times are preserved rather than pretending replies are an atomic snapshot. Command time can only be bounded to sampling intervals and physical observation.

### Manual Block In fallback review

**Not safe to reuse unchanged for the requested policy.** The current presentation predicate waits ten simulator seconds stopped/braked in TaxiIn but offers confirmation when engine data is invalid **or the aircraft is away from the destination**. `ConfirmBlockIn` itself only checks TaxiIn; the latched confirmation can bypass the destination block. This is existing behavior, not introduced by this continuation.

Proposed minimal hardening: one shared eligibility evaluator used both by the snapshot/button and at command execution; require recorded ON, valid destination proximity, on-ground/stationary/brake, the existing ten-second parked interval, fresh coherent data, matching active-flight identity and a known limited capability without reliable contradicting evidence. Clear pending confirmation on every interruption listed above. Do not treat transient invalidity as known unsupported capability. After acceptance, the existing single IN transition and exact completed history ID/PIREP idempotency remain authoritative. This is a proposal only; neither the off-destination override nor the current completion thresholds have been changed yet.

### Required future shutdown regression matrix (not implemented tests)

- Verified two- and four-engine intentional shutdown, including residual spool/fuel-flow tails.
- Brake with engines running; taxi hold; single-engine taxi; partial cutoff; missing required engine index/count.
- Engine failure/fuel starvation while masters remain ON; unavailable or mirrored LVars; conflicting valve/combustion data; nonfinite/noisy zeros.
- Wrong destination, missing ON, wrong aircraft/flight/session identity, stale receipt or simulator timestamps.
- Movement, brake release, relight, pause/slew, time reversal/gap, disconnect/reconnect, restart during confirmation.
- Limited capability manual fallback, direct command invoked when the UI predicate is false, and no automatic downgrade from invalid evidence.
- Exactly one IN, completed history row and PIREP across retries/recovery; historical schema compatibility without manufactured intent.
