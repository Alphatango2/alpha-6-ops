# 7.24C addendum — engine shutdown / PIREP eligibility

Read-first investigation, 28 September 2026. **No production code, completion thresholds, timers, profile data, frozen build, or Map V2 scheduling work changed.** This is a proposal, not an implemented correction. The parked C1 map test is not evidence for this flight's shutdown behavior.

## Finding

JST776 confirms a substantial interval between reported combustion loss and automatic completion. Both engines first report combustion false at **22:26:32.2787399Z**. The saved effective IN is **22:27:29.2802352Z**, **57.0014953 seconds later**; the phase actually becomes Complete on the **22:27:33.2773437Z** sample, **60.9986038 seconds later**.

The dominant final blocker is the generic engine classifier's **fuel flow ≤1 lb/hour per engine** condition. N1/N2 are already below its Off thresholds nearly 28 seconds before fuel flow meets that condition. Two seconds of engine confirmation and a separate three-second phase debounce follow. The phase debounce takes 3.997 seconds with this sample timing.

**The log does not record engine-master/fuel-cutoff commands.** It records combustion, starter, fuel flow, N1/N2 and oil pressure. Command-to-IN latency and individual command order are therefore unavailable. Combustion loss is the earliest supported shutdown proxy; it is not proof of an intentional pilot command.

## Current completion logic

1. `PhaseDetector` must already be in **TaxiIn**. Normally this follows a confirmed ON; a bounce/go-around returns it to Airborne. It tests phase rather than separately checking a stored ON event.
2. The coordinator normally requires current position within **5 NM** of the final filed route point, or catalog destination if that point is absent. Explicit pilot confirmation is the existing override.
3. The default aircraft ground profile requires **on ground**, **groundspeed <0.5 kt**, **parking brake SET**, and **`EngineDataValid && !EnginesRunning`**. Every current family resolves to this default profile.
4. `SimConnectSource.OptionalSensors.Enrich` derives those aggregate engine fields from `EngineEvidenceTracker`; they are **not direct equivalents of the raw combustion booleans**. Binary engine state is valid only when engine count is known and every assessed engine is Off or Running. Starting, Stopping and Unknown make the aggregate invalid.
5. The generic classifier's Off path requires prior observed Running, fuel flow in **[0,1] lb/h**, N1 in **[0,3)%**, and N2 in **[0,5)%**, subject to earlier classifier branches. Off must remain the candidate for **two simulator seconds**. Valid combustion can establish Running, but combustion becoming false does not directly establish Off.
6. The phase candidate must then persist for **three simulator seconds**. A contradictory observation, pause, slew or >15 s sample gap resets the phase candidate; duplicate/out-of-order timestamps do not advance it. Sample timing explains this flight's 3.9971085 s confirmation interval: the preceding sample was only 2.9972153 s after the candidate began.
7. Once Complete, no further phase transition produces a second IN. Actual IN is the original candidate timestamp. Subsequent samples and duplicate observations do not create another milestone.
8. R3 PIREP eligibility is Complete plus actual IN. Current C1 additionally requires an available history store and the exact completed history identity. Submission requires assignment, Complete, IN and the completed row; the database requires that row to be Complete and avoids another PIREP event. There is **no separate post-shutdown PIREP waiting timer**.

The coordinator's separate **10-second** parked/braked timer controls availability of **manual block-in confirmation** when engine data or destination verification is unavailable. It does not delay normal automatic IN and was not the cause here. `pilotConfirmedBlockIn=false` in JST776's persisted PIREP; no manual confirmation event appears.

Disconnect supplies no new observations, but the current candidate/parked timers are not universally cleared directly by `MarkLiveUnavailable`; gap/continuity handling supplies other guards. Do not claim that the existing code independently proves every rapid-reconnect false-positive case. The proposed evidence must be connection-generation scoped, with a fresh confirmation window after reconnect. Similarly, the current five-NM/engine-Off predicate cannot distinguish both engines failed from both engines intentionally commanded off if the remaining terminal conditions coincide.

PIREP persistence and closeout run before the workspace's decorative `TRANSMITTING` animation. The animation does not gate eligibility or durable submission.

The aggregate remains invalid from 22:26:36.2872009 to 22:27:29.2802352, despite continuing raw engine telemetry. It changes from Stopping to Unknown as the decay slows, then finally Off when residual reported flow meets the threshold. This is a **semantic coupling of terminal completion to generic physical-engine assessment**, not evidence of a minute-long PIREP timer or missing telemetry.

**Does S4 wait for physical spool-down? Yes, in the sense that automatic completion inherits low-spool and near-zero fuel-flow requirements. No, it does not wait for literal N1/N2/RPM zero. In JST776, the residual reported fuel-flow tail is the last and dominant condition.** It is not possible to establish from this log whether residual reported flow equals physical injection after flameout; it must not be called actual continuing combustion.

## Code change justified: YES — proposed, not yet safe to enable from existing fields alone

A targeted separation of **terminal shutdown intent/evidence** from **engine mechanical state** is justified. Simply lowering thresholds, treating Stopping/Unknown as Off, or trusting `EnginesRunning=false` while its validity flag is false is not justified.

### Proposed minimal change

Keep the current per-engine start/run/spool-down monitor and its event wording intact. Add one completion-specific, default-unavailable shutdown-evidence result. Its positive state must require complete coverage of the known engine set, fresh validated shutoff/master/fuel-cutoff intent for every required engine, fresh combustion-absent evidence from a channel proven usable for that aircraft, and no contradictory running/start/relight evidence. Residual N1/N2 or an add-on's decaying fuel-flow report must not by itself negate a **verified intentional shutdown**.

Consume that result only in the terminal block-in decision, with an existing ON milestone, TaxiIn/on-ground, destination verification, <0.5 kt, brake SET, same flight/connection, unpaused/unslewed valid observations, and the **existing three-second phase confirmation**. Do not invent another arbitrary timer or backdate IN to an unobserved cockpit command. Preserve exact-once IN, exact history identity, and the existing PIREP transaction/closeout ordering. Distinguish the stored completion-evidence source for review; optional fields must remain backward-readable.

**Important safety prerequisite:** `GENERAL ENG COMBUSTION` is an observed engine state, not a command. JST776 has no engine-master/fuel-valve intent or engine-failure discriminator. Both-engine failure or fuel starvation can also produce combustion false. To meet the requested failure protection, command-channel capability must first be established per supported aircraft; where intent cannot be verified, terminal completion needs explicit parked pilot confirmation. Keeping the current generic Off fallback as unconditional automatic authority would retain the same all-engine-failure ambiguity.

This may change automatic-closeout availability for aircraft with unsupported command channels, including add-ons that already need the A220 fallback. That compatibility decision and its recorded-flight replay implications must be reviewed before implementation. Do not advertise a universally safe one-line combustion shortcut. The first required implementation evidence is a recorded command/state trace showing actual master/cutoff transitions, not an invented timestamp added to JST776.

### Required regression tests before enabling the change

1. **Exact JST776 baseline:** preserve original hashes, reconstruct all 6,145 states and four milestones, retain the original PIREP actuals. Do not relabel hypothetical earlier IN as an observed result. Test legacy records with absent new fields explicitly; document the legacy replay policy.
2. **Validated intentional shutdown:** two-engine and four-engine fixtures with all required cutoff commands, combustion absent, nonzero residual spool/flow, parked at destination after ON. Complete once after the unchanged stability interval; keep each mechanical engine event independent.
3. **Engine-set integrity:** single-engine taxi, one engine still running, missing/unknown/changing engine count, duplicate indices, and an unreported third/fourth engine must block automatic terminal shutdown.
4. **Failure versus intent:** one-engine failure, both-engine failure, fuel starvation and temporary combustion loss with commands still ON or unavailable must not auto-complete, even if brakes are set and RPM eventually reaches zero.
5. **Taxi/position:** temporary brake/hold, rolling at or above threshold, brake release during confirmation, wrong destination, invalid position, no ON, and go-around must reset/block completion. Airport proximity alone must not imply a verified gate stand.
6. **Validity:** unsupported always-zero combustion (A220 case), stale/missing sensor packets, noisy booleans, temporary zero/invalid N1/N2, startup defaults, relight, and contradictory positive combustion must not produce a false terminal state. Prove capability before trusting a zero.
7. **Clock/connection:** pause, slew, frozen/reversed/duplicate simulator timestamps, long gaps, short disconnect/reconnect and source-generation changes must never accumulate stale shutdown confirmation. Reacquire fresh evidence without losing prior OUT/OFF/ON.
8. **Once-only persistence:** repeated terminal samples, page changes, graceful/abrupt restart during confirmation and after Complete, repeated PIREP submission, unavailable/locked database and old recovery files must retain one IN, one original history row and one PIREP. No animation dependency.
9. **Compatibility and native proof:** run affected Core/Desktop/engine/recovery regressions, nine historical replays and JST776 without rewriting source evidence; separately validate the actual Fenix command-to-completion path and the A220 fallback. Only then quantify expected improvement and enable the path for supported aircraft.
