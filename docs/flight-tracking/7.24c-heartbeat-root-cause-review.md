## Definition and provenance

`MapContentionChecks.RunFlightAsync` creates a `DispatcherTimer` on the WPF UI
dispatcher, with **Background (4)** priority and **20 ms** interval. A monotonic
`Stopwatch` records elapsed milliseconds at the start of each Tick, then restarts.
This measures **callback-to-callback elapsed time**, including the nominal interval,
timer promotion/wakeup delay and runnable queue wait. It is not pure queue latency,
not lateness after subtracting 20 ms, and not input-to-display latency. The initial
stopwatch starts shortly before `timer.Start`; the first interval includes that
small setup span. The timer reschedules after its callback, rather than issuing an
independent fixed-rate stream of queued callbacks.

Sequence: Start/previous Tick → Inactive dispatcher operation → due-time promotion
to Background → eligible queue wait → Tick → elapsed interval recorded. Detailed
traces distinguish initial Inactive residence from promotion-to-start wait. A
Normal continuation ends the original observation after feed completion and 100 ms;
its last unfinished interval was historically absent from the maximum. This review
retains that pending age separately without changing the original assertion.

The unchanged acceptance rule is:

`stressed maximum < 500 ms && stressed maximum <= max(150 ms, baseline maximum + 100 ms)`.

The comparison is between two sequential short, complete 395-sample flights, not
equal-duration percentiles or a calibrated statistical confidence interval. The
baseline has no snapshot projection pump; **the initialized visible composition
renderer still exists**. The stressed arm adds projection/map updates and one
1,000 ms JavaScript busy loop. The flight source advances ten simulator seconds
per nominal 20 ms wall-clock emission. Both use real isolated flight coordinator,
history, recovery and PIREP paths, with a synthetic source.

Git introduces the exact numerical rule in `8ab65cc` (Checkpoint 7.22). Its plan
requires checking dispatcher contention while stalling the renderer; its report
records 121.0/139.7 ms baseline/stressed maxima. The reviewed specification, plan,
commit and report do **not** document an empirical derivation for 500, +100 or the
150 ms floor. Treat these as the existing engineering acceptance budgets; do not
invent a human-perception study or claim that they came from a pilot requirement.
The original purpose was protection against browser/map work blocking the flight
runtime/UI dispatcher. A delayed synthetic scheduling sentinel is evidence of
delayed Background service; it does not by itself establish visible input lag.

## Priority and possible user impact

Input (5), Loaded (6), Render (7), DataBind (8), Normal (9), Send (10), already
running callbacks and native dispatch can execute ahead of Background. Other
eligible work at the same priority also matters. The flight runtime uses Normal;
the corrected short map handoff uses Render. The production program monitor uses
Background, so sustained starvation is not irrelevant just because mouse handling
can remain smooth. [Priority definitions](https://learn.microsoft.com/en-us/dotnet/api/system.windows.threading.dispatcherpriority?view=windowsdesktop-10.0).

WPF's `ProcessQueue` permits its lower-priority range only when native pending-input
checks permit it. Foreground requests can replace the background-processing timer
with a posted message. Thus many brief render/native turns can delay a ready
Background operation without occupying the full interval as managed callback CPU.
This describes a mechanism to investigate, not proof that every historical delay
has the same cause. [WPF Dispatcher source](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/WindowsBase/System/Windows/Threading/Dispatcher.cs),
[DispatcherTimer source](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/WindowsBase/System/Windows/Threading/DispatcherTimer.cs).

The current runtime is .NET/WindowsDesktop 10.0.11; the linked main-branch source
is explanatory and is not falsely represented as a byte-identical runtime build.

## Evidence preservation and comparison design

The predeclared series contains 12 fresh-process runs. Tracing order is
OFF/ON/ON/OFF/OFF/ON/ON/OFF/OFF/ON/ON/OFF. Each includes two 30-second map contexts,
alternating idle-first/normal-first, followed by the unchanged complete-flight
baseline/stressed pair on a fresh renderer. No slot is retried or selected for a
favorable result. All original 98 assertions remain active per process.

Idle means a loaded composition renderer without new map offers. Normal means a
one-aircraft synthetic map snapshot offered by an independent worker at 1 Hz.
These contexts do not feed the Operations flight presenter or native SimConnect.
The inherited diagnostic shell has its dashboard clock disabled. This condition
is recorded, not altered by the characterization. The main shell is 3440×1400 DIP;
the separate composition diagnostic viewport is 1134×611 DIP.
Idle-first begins before its first flight snapshot/reveal; idle-after-normal
retains the previously displayed map. They are labeled separately in the evidence,
not described as identical active-flight production workloads. No physical input,
workspace navigation or deliberate resize occurs inside these measurements.

The existing detailed observer records dispatcher post/promotion/start/end/abort,
layout notifications, presentation/recovery activities, GC marks and 250 ms CPU/
thread-state samples. The added diagnostic observer records native message IDs,
WPF input notifications, browser message types and periodic zero-time pending-queue
queries. It never consumes a message, changes `handled`, injects an input, posts
an extra UI sentinel or subscribes to `CompositionTarget.Rendering`.

The native query uses `MsgWaitForMultipleObjectsEx` with INPUTAVAILABLE and zero
timeout. Results are snapshots, not a trace of each internal WPF decision. System
events can produce a wake indication without a corresponding requested message;
the bit categories must not be overinterpreted. Observer CPU/memory cost remains
part of the measured run; the on/off split does not authorize subtracting it.
[API semantics](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-msgwaitformultipleobjectsex).

## Decision

**Classification: UNRESOLVED.** The measured mechanism is **selective ready
Background-queue deferral during continuing native/composition/render traffic**,
not a 345 ms application callback or an observed telemetry halt. The traffic now
has a verified native-window owner. The exact relationship among CoreMessaging
work, WPF's pending-input decision, background timer cancellation/wakeup and OS
scheduling is still not captured at the required causal depth. Many brief
higher-priority turns occur, but their managed execution does not explain the
whole delay as CPU occupancy. No kernel context-switch/wait-stack trace exists;
the current tool process has a non-elevated Windows token. No elevation or machine
configuration change was attempted.

**Production change required: NO justified change at this stage.** This is not a
finding that production is proven defect-free. The evidence does not identify a
specific S4 operation to correct safely. Moving the observer's priority, inserting
a polling wakeup, changing frame cadence, ignoring idle/tail samples or loosening
the thresholds would mask or alter the phenomenon before its cause is established.
None was done. T2 capability qualification, shutdown authority, operational flight
logic, map restoration and authoritative telemetry remain unchanged.

There are demonstrable **metric limitations**, not grounds to discard the gate:
callback interval is not input latency; a maximum-to-maximum sequential comparison
has a variable reference; and a stopped timer can have an unfinished interval.
The new observations preserve the tails, and the existing predicate is unchanged.
Background service is still a legitimate starvation sentinel. It cannot yet be
reclassified as a harmless metric defect or external variance solely because
native panning was smooth.

Recommended complementary product measurements: independently timestamp an actual
pointer event through WPF/browser receipt, camera change and presented frame;
retain map offer→post→ACK as a distinct delivery measurement; and correlate
telemetry arrival→consumption plus Background-service age. Pair these with native
message/wait stacks in the same full Operations workload. Explicitly approve any
future metric policy on product behavior before changing acceptance; do not
substitute a higher-priority timer with the old numerical limit.

**Existing threshold changed: NO. T2 native parked validation cleared: NO.
7.24C: NO-GO.** No T2 installation or native simulator run occurred.
