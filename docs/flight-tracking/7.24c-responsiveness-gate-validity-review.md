# 7.24C — RESPONSIVENESS GATE VALIDITY REVIEW

**Recommendation: HEARTBEAT VALID BUT ACCEPTANCE MODEL IS WRONG.** The Background
heartbeat measures a real scheduling delay, but its maximum callback interval is
not a validated standalone measure of user/flight responsiveness. We can reach
that conclusion without identifying every native CoreMessaging scheduling detail.
This is a gate-validity decision, not a claim that all latency is harmless.

**Existing threshold modified: NO. Production change justified by this review: NO.
T2 installation recommendation: NO at this stage.** The current gate remains failed
under its unchanged rule. Adopt an explicitly approved product-metric contract and
close its identified coverage gaps before clearing T2; further open-ended native
message attribution is not a prerequisite for designing that contract. No app,
installer, simulator, build or new performance trial was launched for this review.

The previous root-cause review and every failed result remain unchanged. This
additive review answers a different question: whether that signal has sufficient
specificity and coverage to decide product acceptance.

## Product requirement being protected

| Requirement | Correct acceptance endpoint | What the existing heartbeat establishes |
|---|---|---|
| User input | Pointer/button/key delivery, pan/camera response, selection and navigation, including focus/scroll behavior | No direct latency measurement; it can warn of contention |
| Visual updates | Current aircraft/route/lighting state reaches a correct visible frame, with intentional interpolation accounted for | Neither browser execution nor frame presentation |
| Tracking responsiveness | Each received sample reaches tracking/phase/event processing promptly, without growing backlog | No sample arrival-to-processing measurement |
| Flight integrity | Complete ordered samples/events, unchanged session identity, correct OUT/OFF/ON/IN and durable PIREP/recovery | No data-integrity measurement |
| Application liveness | Meaningful requested UI/browser/runtime work makes progress; pending required work cannot starve indefinitely | Service of this particular Background timer, not all required work |

These requirements remain separate. A responsive pointer cannot compensate for
lost telemetry; complete eventual telemetry cannot prove prompt processing; a
browser ACK cannot prove a correct visible frame.

## What Background heartbeat actually measures

`MapContentionChecks.RunFlightAsync` starts a nominal 20 ms Background-priority
DispatcherTimer. A monotonic Stopwatch measures callback-start to callback-start.
The interval contains the nominal delay, due-time promotion/wakeup and runnable
queue wait. It is not a 20 ms deadline guarantee, pure queue latency, or a sample
of physical input latency. It restarts after a Tick rather than independently
posting a fixed-rate stream. The latest characterization also retains unfinished
tail ages separately; the original assertion evaluates completed intervals.

Background (4) yields to higher dispatcher priorities. WPF additionally gates its
lower-priority processing on pending native input/events/posted messages. Foreground
requests can replace its background timer with a queue message. This permits
short Render (7) and Normal (9) work to continue while Background remains ready.
[Priority definitions](https://learn.microsoft.com/en-us/dotnet/api/system.windows.threading.dispatcherpriority?view=windowsdesktop-10.0),
[Dispatcher source](https://github.com/dotnet/wpf/blob/v10.0.0/src/Microsoft.DotNet.Wpf/src/WindowsBase/System/Windows/Threading/Dispatcher.cs),
[timer source](https://github.com/dotnet/wpf/blob/v10.0.0/src/Microsoft.DotNet.Wpf/src/WindowsBase/System/Windows/Threading/DispatcherTimer.cs).
The tagged source explains the mechanism; it is not claimed to be a byte-exact
analysis of installed WindowsDesktop 10.0.11.

**Background is suitable for observing low-priority service/starvation, but not as
the sole user/flight release sentinel.** A prolonged wait can harm a real consumer
at that priority. It does not, by itself, demonstrate a global UI stall. Raising
the sentinel priority would change the question and is not the proposed fix.

## Idle/stressed inversion

The preserved 12-process series contains 48 arms and 7,862 completed intervals:

| Condition | P95, ms | Maximum, ms |
|---|---:|---:|
| Accelerated flight baseline | 162.8576 | 429.3428 |
| Accelerated stressed flight | 152.5093 | 497.0016 |
| Loaded map, no new offers | 924.0126 | 3128.1934 |
| Map offers at 1 Hz | 751.3485 | 1472.1431 |

“Idle” describes the absence of new map/flight data, not an inactive native or
composition message stream. During the worst idle interval, Render callbacks
arrived approximately every 4.17 ms. Making less application work therefore does
not necessarily create a quiet native queue in which Background can run.

The flight harness independently emits approximately every 20 ms and posts Normal
runtime work. That changes wakeups and opportunities to drain native/dispatcher
queues. Earlier 7.24A.2 controls also found worse tails after producer shutdown,
and p95 99.83 ms with extra Normal polling versus 258.37 ms with an Input probe.
These are evidence of workload/wakeup sensitivity, not permission to add polling.
The exact amount of the inversion attributable to any one wakeup is unproven.

The detailed idle trace shows promotion after about 32.832 ms, followed by
3095.359 ms of ready wait. Thus its multi-second gap is predominantly **after**
promotion, not simply a late 20 ms OS timer. Pending native indications occur
throughout, consistent with the WPF mechanism. Another failing process identified
the observed `UserAdapterWindowClass` as owned by CoreMessaging.dll. That identifies
an intermediary, not a defective Windows function or WebView call stack.

Timer coalescing, Windows power policy and browser/GPU scheduling were not
independently varied or traced, so they are **not established causes**. No new
power/timer setting, priority or renderer change is justified. Both traced and
untraced contexts show long gaps, excluding tracing as a necessary cause.

Comparability limits also matter: contexts run 30 seconds; accelerated flight arms
run roughly 8–10 seconds. Their maximums have different exposure lengths. Both
the flight baseline and stress arm retain a composition renderer; baseline means
no projection feed, not no browser. The context shell clock is disabled, and its
separate map viewport is not the complete live Operations presenter. These are
characterizations, not interchangeable production workloads.

## 3.128s idle heartbeat interval

Exact preserved window: **10,418.6322–13,546.8256 ms** in run-09/context-idle,
after the normal map context had already displayed data.

| During that same interval | Observation and limit |
|---|---|
| WPF work | 750 Render callbacks, three hit-test callbacks and three input-staging callbacks; 750 layout notifications |
| Render callback spacing | Median 4.1667 ms, maximum 4.4582 ms between starts inside the window; not frame/GPU timing |
| Callback execution | Completed envelopes total 21.4980 ms; longest 0.1493 ms; no unclosed operation obscures the window |
| Native messages | 2,258; all 250 sampled pending-queue observations indicate posted work, 249 also indicate input |
| Input | Six generic PreviewInputReport/InputReport notifications; no commanded pointer/click/pan action or end-to-end input measurement |
| Telemetry | No producer in this condition; no arrival or processing latency can be inferred |
| Map/browser communication | No new map offers or ACKs in this interval; browser response latency is unmeasured |
| Actual visible image | No presented-frame trace or video; continued Render callbacks do not establish visible frame correctness |

The UI dispatcher was not globally deadlocked throughout these 3.128 seconds.
The timer was selectively delayed. We cannot retroactively claim that a user
click, new telemetry sample or new map offer would have completed promptly in this
particular idle interval because those operations were not requested.

## Correlation with physical input

Existing C1/T1 parked observations reported no hitch and no F9 marker. In T1's
**1,483.3783 ms non-timer Background queue wait**, offline correlation finds:
133 left-drag notifications with message age at most 16 ms, 358 Render callbacks,
one received telemetry sample processed in 0.3545 ms, and two map-related posts
queued for at most 0.0411 ms. That is simultaneous evidence, not a comparison of
unrelated whole-run maxima. WPF message age is coarse and is not input-to-pixel
latency; notifications are not independent hardware samples.

Separately, corrected synthetic WPF-to-trusted-browser input completed in
1.2157, 2.3872 and 2.5029 ms across three full Operations runs; the frozen T2
binary with external input preparation recorded 1.8664 ms. These establish the
corrected input harness's behavior under its original deadline. They were not
performed during the 3.128-second interval and do not certify native T2 input.

The earlier synthetic failure was a missing coordinate-bearing mouse move before
a button press, not proven production focus breakage. Its failed and corrected
results remain separate. The historical physical input/layout defects and JST776
airborne hitch remain authoritative failures; none is erased by this review.

## Correlation with map presentation

New offline correlation of the **existing** 1 Hz contexts gives 360 offers and
360 ACKs, with maximum map-dispatch queue wait **0.2837 ms**, despite long
Background intervals. In six traced contexts, 25 offered updates overlapping
heartbeat gaps of at least one second reached ACK within **10.6742 ms**.

For gaps of at least 500 ms, 113 overlapping offer/ACK pairs include two initial
updates taking up to **938.3023 ms**. Those are retained. The other 111 pairs take
at most **10.8803 ms**. Initial-update latency deserves its own startup/first-paint
budget; it is not silently excluded from overall results or deemed acceptable by
this review. Pairing uses verified ordered 30-offer/30-ACK streams with no
coalescing/rejection, not unrecorded sequence IDs. **ACK is not a rendered frame.**

C1's actual 4,280.8266 ms Background map handoff was a meaningful delayed product
operation. The existing Render-priority correction remains necessary and intact.
T1's map queue maximum was 1.347 ms. The controlled 750 ms Render-pressure check
subsequently delivered a post in 0.4491 ms and ACK in 1.124 ms. A fast Background
heartbeat cannot detect every browser/GPU freeze either: the intentionally blocked
browser can coexist with continuing runtime/dispatcher work.

Restoration is a separate endpoint: the preserved 157-check suite passed, with
18/18 same-renderer workspace returns. Correct-visible-state observation took
at most 332.7414 ms; cold initialization took 1754.1208 ms. These are measured
baselines, not newly adopted deadlines or measurements inside the idle gap.

## Correlation with telemetry

In the new series' failing relative-gate interval (345.9318 ms), all 16 samples
processed during the gap took at most **7.3881 ms** from diagnostic emission to
processing. Six traced stressed flights each retain 395 serial samples; their
whole-arm maximum processing delays range from 19.0732 to 24.7451 ms.

Native T1 retains 112/112 trace arrivals, p95 1.226 ms and maximum 56.684 ms
arrival-to-processing; its 159-sample journal covers a longer interval. These
measure application receipt onward, not simulator updates never delivered to S4.
The untraced original 513.2116 ms heartbeat failure cannot supply same-gap
telemetry latency retrospectively. Its exact sample/event/state equality and
whole-arm map queue maximum 3.226 ms remain available.

## Correlation with data integrity

All 9,480 authoritative samples in the 12 paired flight runs were retained.
Paired telemetry timelines, operational events, recovery/history and PIREP results
match. The original 513.2116 ms failure and its unchanged passing recheck remain
separate evidence. The later relative failure, 345.9318 ms versus a 304.0020 ms
bound, also remains failed. A passing integrity check proves neither pixel
responsiveness nor bounded sample latency by itself.

Existing verification is retained, not rerun or counted as new: full regression
1,953 passed / 0 failed / 2 native-only skipped; 11/11 replays and 100,632 replay
samples. Native destination/recovery/PIREP validation of T2 is still outstanding.

## Real starvation exposure and application liveness

Background is not unused production capacity. The one-second `dashboardClock`
defaults to Background; its callback refreshes displayed time, local weather and
Operations. The 15-second `ProgramMonitor` heartbeat also uses Background.
The T1 trace shows a dashboard timer **1085.9060 ms ready wait**, excluding its
intentional one-second inactive interval. During that ready wait, 931 physical
drag notifications continued and a telemetry sample processed in 0.6061 ms.

This is a real delayed periodic presentation callback and belongs in a freshness
contract. It is not proof of lost flight tracking, visible flicker, or a continuous
application hang. The final 20 ms sentinel does not measure that callback's own
deadline, payload freshness, or eventual progress. Blanket “harmless idle variance”
would therefore be unjustified, as would declaring the whole UI frozen.

Existing negative controls detect deliberately injected 600 ms UI blocking via
pending-work age, a 650 ms UI block via queued input, and a 650 ms JavaScript block
via **unfiltered** browser frame intervals. Those controls are useful detection
evidence. A normal RAF callback still is not a hardware-presented frame, and
synthetic CDP input does not test the physical composition pointer route.

## Original 7.22 gate rationale

Commit **8ab65cc**, `Checkpoint 7.22: integrate opt-in Operations Map V2`, added
the assertion. Specification Part 18 calls for deliberately stressing the map
and proving uninterrupted authoritative processing, events, history, phases and
PIREP, while measuring Dispatcher impact. The plan added a heartbeat comparison.
The report recorded baseline/stressed maxima 121.0/139.7 ms and matching flights.

No linked known user-visible freeze is documented as the origin of this numeric
rule in the reviewed specification/plan/report/commit. It was preventative
integration isolation coverage. The later real layout/input/map failures must
not be retroactively described as the rule's original calibration experiment.

**<500 ms derivation:** none documented in those records.

**Baseline +100 ms derivation:** none documented; likewise for the 150 ms floor.
The difference between two short sequential maximums is not a calibrated paired
latency distribution. A worse baseline relaxes the relative bound and a faster
baseline tightens it without changing the product requirement.

**Current heartbeat classification: conservative engineering heuristic, enforced
as a hard test; useful diagnostic, not established product-derived SLA.** There
is evidence of deliberate introduction as an assertion, not evidence of an
accidental decision. Subsequent worker/coalescing changes, recovery persistence
and renderer retention altered workloads. Most directly, the actual map handoff
now uses Render, while authoritative dispatch uses Normal. The Background
measurement is unchanged but less directly representative of those critical paths.

## Recommended responsiveness acceptance model

Adopt a multi-metric contract explicitly, before changing gate disposition:

| Area | Proposed release evidence | Numerical-policy treatment |
|---|---|---|
| Integrity | Zero missing/duplicate authoritative samples; ordered events; identical accepted flight identity/state; exact-once IN/PIREP; durable restart/recovery | Retain existing exact invariants; these are requirements, not statistical allowances |
| Input | In-bounds trusted synthetic actions plus installed physical pan/zoom/click/key/focus/navigation; measure delivery and resulting camera/selection response | Retain existing test deadlines; the 1500 ms synthetic correctness timeout is not a desired UX budget. Native 0–16 ms WPF age and no-hitch observations are references, not an end-to-end threshold |
| Visual freshness | Offer → dispatch → post → ACK → correct frame, with separate cold creation, restoration and steady active-motion results | Use measured T1/normal-context delivery and restoration distributions as calibration references; account for the existing 200 ms projection cadence and intentional interpolation. Do not label ACK as display latency |
| Tracking latency | Independent source arrival → authoritative processing/durability, outstanding queue depth/age, no growing backlog during interaction and a browser stall | Compare against native C1/T1 and controlled matched workloads; preserve every sample. Existing p95/max values are observations, not new universal ceilings |
| Liveness | Actual required work completion plus bounded independent watchdog/progress observation, pending-tail capture and injected UI/browser stalls | Keep distinct UI, browser and flight-progress signals. A successful high-priority callback alone cannot certify low-priority freshness |
| Periodic presentation/health | Measure actual dashboard-clock/Operations-refresh and health-writer service delay/freshness | Include the measured late dashboard callback; approve a requirement for these consumers instead of borrowing the unrelated 20 ms sentinel limit |
| Background heartbeat | Retain raw intervals, promotion/ready wait, long-gap counts, unfinished tails and correlations; trigger investigation on drift | Recommended diagnostic role in the future contract; current predicate stays unchanged until approval |

No new latency numbers are proposed as pass/fail thresholds here. Current sample
sizes and endpoints do not justify converting observed maxima into universal
limits. Before adoption, predeclare target hardware/scaling/workload, cold versus
steady conditions, fixed observation lengths, p95/p99 and worst/pending ages, then
calibrate against physical acceptance and intentionally visible failure controls.
Retain all trials; no retry-until-pass or larger allowance chosen above a failure.

The smallest remaining evidence work is targeted: measure input-to-camera/visible
response and sample-to-correct-frame progress during normal active interaction,
retain the passive Background trace for correlation, and measure the actual
periodic refresh consumers. Do not add a high-rate probe that changes dispatcher
wakeups and then use its improved sentinel score as proof. Missing operations in
the historical idle interval must remain marked unmeasured.

## Decision and evidence

- **Existing heartbeat threshold modified: NO.** No assertion, priority, timeout,
  retry, policy or previous result changed.
- **Production change justified: NO.** No new safely targeted production correction
  follows from this review; the existing map handoff correction remains intact.
- **Recommendation: HEARTBEAT VALID BUT ACCEPTANCE MODEL IS WRONG.** The evidence
  supports revising what acceptance measures, not declaring the signal invalid or
  all product responsiveness already proved.
- **T2 installation recommendation: NO**, pending explicit acceptance-model
  approval and the specific coverage above. This is not a demand to solve every
  CoreMessaging detail before reconsidering the gate. No installation/7.25 work.
